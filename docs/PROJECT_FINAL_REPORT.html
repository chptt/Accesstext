Reading Messages Through Android's Accessibility Layer

Can a messaging app's visible screen be rebuilt into individual message records — and how much of that is actually proven?

Project: Grooming-Risk Research Prototype  ·  Package: com.example.groomingresearchdemo v1.0 (versionCode 1)  ·  Report date: 2026-10-20  ·  Platform: Android (minSdk 24, target/compile SDK 36)

Plain-English summary — what this tool does

The researcher opens a messaging app on a test phone, switches back to this tool and presses one button. The tool takes a single "shape read" of whatever screen is currently visible — using the same Android feature a screen reader uses for a blind user — and reports what it found. It reads the screen once: no scrolling, no clicking, no history navigation, no background running, and it cannot send anything.

Two readings come from that one look at the screen. The first counts structure — how many elements are on screen, how many expose text, how deep the layout goes. That is the compatibility evidence, unchanged from the earlier phase. The second, added now and only if a box is ticked, tries to go further: work out which elements are individual chat messages, put them in reading order, and rebuild them as message records.

The honest headline

What works: the full pipeline builds, passes 160 automated tests, installs and runs on Android 15, and has been executed against real Instagram three times without crashing. It correctly refuses to invent senders, timestamps or message boundaries.

What is not proven: whether any of it is correct on a real app. Accuracy on real conversations is NOT MEASURED, because no real screen has yet been transcribed by hand to compare against. No Instagram, Instagram Lite, WhatsApp, Signal, Telegram or Google Messages compatibility claim is made here, and the counts on page 8 must not be repeated as "messages extracted".

1. Background, objective and boundaries

Context. The parent project investigates whether automated assistance can help identify grooming risk in conversations, and any such system needs message-level text — who said what, in what order. Messaging apps offer no research API, so the question becomes: does Android's own accessibility layer already expose enough to reconstruct messages, without hacking, root or bypassing anything? Objective for this phase: extend the existing prototype so that visible, accessible UI elements can be reconstructed into message-level records for an explicitly selected conversation the researcher is authorised to study — and report honestly how well that works.

What "accessibility layer" means here, in one paragraph

Android gives an app a permission-free way to describe its own screen to assistive technology: every visible widget appears as a node in a tree, each with a class name (TextView, Button), optional text, an optional description, a rectangle on screen, and child nodes. A screen reader reads this tree aloud; our tool reads the same tree. It is the app volunteering information to the operating system — not a hidden channel, not a security bypass — and it works only while that screen is actually on display.

Hard boundaries accepted by this build

Allowed

  • One read, triggered by one deliberate button press
  • Only the currently visible screen
  • Only the app the researcher selected
  • Text held in memory, for that one inspection
  • A visible "armed" indicator and a Stop/Cancel action

Never

  • No scrolling, clicking, sending or history navigation
  • No background polling, timers or scheduled scraping
  • No screenshots, recording, clipboard, keystrokes, notifications
  • No private app databases, network traffic, encryption bypass, hidden APIs
  • No deleted, hidden or off-screen content; no upload of any kind

Two consent gates that are deliberate, not inconvenient

Gate 1 — the accessibility toggle. Android only lets a human turn on an accessibility service, from Settings, after reading what it can do. This harness will not do it by adb, and has refused three attempts to work around that (a settings write, a cross-app UI dump, synthetic taps). The consequence matters: no automated real-app validation is possible, so every real-device row in this report came from a human pressing a button. Gate 2 — the extraction tick-box. The message-level stage is off unless explicitly ticked, and the choice is captured at the moment of arming; unticking afterwards cannot widen or narrow an inspection the researcher already consented to. The target app is frozen the same way.

2. What the tool is not

  • Not a monitor. No polling, no timer loop, no retry, no background service. Each qualifying event schedules one deferred read — a single postDelayed of 1.5 s, so a transition frame can settle before the one snapshot — and an arm token rejects it if the researcher cancelled or re-armed in between. There is no coroutine scope, Timer, AlarmManager or WorkManager; the only coroutine imports are StateFlow, used to publish UI state after something already happened.
  • Not a scraper, and not a detector. It cannot browse contacts or walk back through history: one press = one screen = one result. No machine-learning model is connected; the adapter refuses uncertain records and the model placeholder returns "Model not integrated", so nothing in this build labels anything as grooming.
  • Not a general result. Eight structural observations and three extraction runs across two apps is a handful, and the spec forbids claiming general compatibility from them.

3. How it works — the pipeline

1 · ArmResearcher presses Start. Consent, service and target are checked; the extraction tick-box is frozen here.
2 · One eventThe target app's window-change event arrives. State flips to EXECUTING before the tree opens, so a second event cannot trigger a second read.
3 · Open onceA lazy provider hands over the accessibility root. If the package does not match, the tree is never opened.
4 · Two passesStructural BFS (unchanged) produces counts. If opted in, an extraction BFS walks the same snapshot.
5 · ClassifyEvery node judged by transparent rules → candidate, ambiguous or rejected-with-a-reason.
6 · ReconstructOrder by on-screen geometry, suppress duplicates, emit records with nullable sender/timestamp.
7 · ReportCounts on the results screen; five independent status gates; text only on a separate deliberate review screen.
8 · ForgetLeaving review, cancelling, revoking consent or changing target destroys the retained text. Counts survive.

The one-shot lifecycle, stated precisely

NOT_ARMED --arm(consent, service, target, extraction?)--> ARMED
ARMED      --qualifying event-->  EXECUTING --root read--> result, back to NOT_ARMED
ARMED      --cancel()-->          NOT_ARMED   (records a CANCELLED result, no stats)
any        --consent revoke / service disconnect / app restart--> forceDisarm(), nothing retained

There is no path back to ARMED without another human press. An app restart does not re-arm; a failed inspection does not retry.

Three layers bound which app can ever be read

LayerMechanismEffect
1 · Configandroid:packageNames in the accessibility service config Android delivers events from six allowlisted messaging apps only; every other app on the device cannot reach this service at all.
2 · RuntimesetServiceInfo() narrowing at connect time The allowlist is cut down to the single app the researcher selected.
3 · LogicarmedTarget equality check on each event Even a matching package's event is ignored unless it equals the frozen arm-time target — verified by anEventFromAnotherPackageLeavesBothTheArmAndTheExtractionFlagIntact.

Allowlist: com.google.android.apps.messaging, com.instagram.android, com.instagram.lite, com.whatsapp, org.telegram.messenger, org.thoughtcrime.securesms. WhatsApp, Telegram and Signal are permitted but not installed on the test image, so nothing about them has been observed at all.

Defensive handling of a tree that misbehaves

Every property read is wrapped individually, so a node refusing one attribute costs that attribute and not the node. A childCount() that throws is counted as a lost subtree rather than treated as a leaf — the tool will not claim "this screen is small" because the platform declined to answer. A node that declares n children but yields fewer is flagged as structure lost, the live signature of a screen changing mid-read. Text and its presence flag come from one read, never two, because the framework may return a different value on the next call.

The node interface was widened without touching the old code path

AccessibilityNodeView is the small interface the whole pipeline reads through, so the real AccessibilityNodeInfo never leaks into logic that must stay unit-testable. Seven members were added — each with a default implementation:

boundsInScreen(): NodeBounds?   isClickable()   isScrollable()   isVisibleToUser(): Boolean?
parent(): AccessibilityNodeView?   nodeId(): Long?   aggregatesDescendantText(): Boolean

Defaults are the mechanism that keeps the original inspector byte-identical: new members are inert unless something calls them, and the structural pass calls none of them. isVisibleToUser() is deliberately nullable — "unknown" and "invisible" drive different decisions and must not collapse into one. aggregatesDescendantText() detects the container-echo case by comparing a node's text against its own children, bounded at 64 children so a screen-wide container cannot stall the traversal. Deliberately absent: viewIdResourceName and any package/install metadata — those are the levers that would turn a research prototype into an app-specific scraper. No classifier rule keys on a package name or view ID, and an unrecognised class such as com.shrug.bubble.CustomMessageText is judged on structure alone (a test proves it).

5. The classifier and the reconstruction rules

Both are pure Kotlin with zero Android imports, so they run on synthetic trees on a normal JVM. The spec asked for a transparent rule-based classifier before sophisticated reconstruction; that ordering was followed, and every exclusion returns a named reason string so the UI can explain a rejection without quoting the rejected text.

Exclusion rules — screen furniture that is not a message

RuleDetection signal (structural, not app-specific)
Navigation labelsChrome phrase list matched on shape; short label in the top band
Search controls"search" phrase, class shape, position
Text-entry fieldsEditText class — the composer, not a sent message
Send buttonsButton/ImageButton + clickable + "send"
Menus, dialogs, headers, profile labelsNamed phrase and class-shape rules
Loading indicators, announcementsReceipt / announcement shapes
Container echoesNode whose text equals its own child's text
Invisible nodesisVisibleToUser() == false → rejected; null → only weakened

Two guardrails exist because naive chrome filters eat real messages: a status word inside a real sentence does not delete it ("did you read it yet" stays a candidate), and short replies like "ok" survive the list. A one-character node is made ambiguous, not dropped — preserving uncertainty is required.

A design bug the tests caught, and what it taught

Writing the classifier tests exposed a layering flaw: low evidence strength forced AMBIGUOUS, which made the CANDIDATE status and the TRAVERSAL_UNVERIFIED order basis unreachable — two of the states the specification requires could never be displayed. Root cause: placement was being decided by the classifier, where it does not belong. Missing geometry is an ordering problem, not an identity problem. The fix split the axes — an unresolved role becomes ambiguous, while a plausible message with no geometry stays a candidate at low strength — and safety moved downstream: the reconstructor refuses a record it cannot order. The rule changed from "weaken the evidence label" to "refuse the verdict", which is where the specification puts it.

The ten reconstruction rules implemented

  1. Order from geometry — visible top-to-bottom position, grouped into row bands.
  2. Structural order only as a named fallback — TRAVERSAL_UNVERIFIED, which caps the result at INCOMPLETE and accepts nothing.
  3. Detect and deduplicate repeated text between parent and child; the child survives.
  4. Never merge adjacent nodes into one message without structural evidence.
  5. Never split on punctuation or line breaks — a three-line bubble is one record.
  6. Alignment-based sender inference is opt-in, off by default, self-labelled as a heuristic. It emits a side token, never a person, and the adapter refuses to promote it into a name.
  7. Never invent timestamps, senders, missing messages or boundaries.
  8. Preserve ambiguity — uncertain records stay visible, marked and counted.
  9. Partial vs complete — clipping, truncation and mid-read mutation all force "partial".
  10. Boundaries unclear ⇒ INCOMPLETE or UNSUPPORTED, never guessed text presented as a conversation.

Record schema

MessageRecord(candidateId, text?, speakerLabel?, timestampMillis?, bounds?,
              confidence, evidence: List<String>, status, visibleOrderIndex?)

candidateId is synthesised per inspection ("i42-0001") and never derived from a framework node id. evidence holds non-sensitive structural reasons such as leaf-node, valid-bounds, geometry-missing — a test asserts no evidence token ever quotes the node's text.

The five status gates

#ClaimIts own criterion
1Inspection completedA terminal COMPLETED outcome with a root read
2Candidates detectedExtraction ran and found ≥1 message-shaped node
3Message structure reconstructedRecords placed in an established order, with boundaries established
4Speaker attribution validatedA rule fired and was validated against an annotated sample
5Complete conversation validatedNot a partial sample and the researcher attests the screen was the whole conversation

Modelled as five independent booleans, not one ordinal enum — an enum invites a level >= 3 check in the UI, which lets level 1 satisfy level 5's display slot by arithmetic. Each unmet gate carries its own reason string, so "no" never looks like a silent failure. Levels 4 and 5 need evidence the app cannot generate itself, so in any unattended run they read "not met" — the correct answer, not a shortfall to design around.

Audit finding on the pre-existing code (documented, not smoothed over): the specification asked that any existing privacy violation be recorded and minimally corrected. None was found. Data-minimisation choices worth naming

  • Booleans before content. The structural pass records "does this node expose text" rather than the text — that is what keeps the compatibility report content-free.
  • Geometry is safe to keep. A rectangle is a position, not a message.
  • Reasons are strings the classifier wrote, such as multiple-text-nodes-in-one-row — never the rejected text itself.
  • One reconstruction at a time. A new inspection replaces the previous one before anything is published, so content cannot accumulate across runs.
  • Published copies are record-free. Session reports and UI state receive withoutRecords(); the full copy is reachable only through the single peek used by the review screen.
Boundary held this session. The researcher asked for the reconstructed text to appear in the terminal. That was refused: terminal output means Logcat, which the privacy section of the spec names explicitly, it persists on the device, it lands in bug reports, and it would carry another person's messages out of the app. The sanctioned route — the in-app review screen — already existed and needed no rebuild. A screenshot of that screen was also declined, because writing the image to a file is exactly the persistence these controls exist to prevent.

Proven: the pipeline executes against a live third-party tree, resolves geometry-based reading order, rejects 40–41 nodes per screen as non-message, never crashed, and kept every log line free of message text across a consent revoke, cancels, four arms and three extractions. Still unproven: correctness. The verdict swung from 11 to 17 to 16 accepted on near-identical structure and the cause is unexplained — either the screen changed or the row-grouping flipped, and unlabelled runs cannot tell them apart. accepted=17 is not "17 messages extracted".

Device-only findings that qualify every future real number: (1) node identity is unavailable on Android — getSourceNodeId() is not public API and reaching it would need a hidden API, so duplicate-visit suppression is unobservable on device and falls back to wrapper identity; (2) with both parent ids null, the "same row" test loses its sibling clause and becomes geometry-only across the whole screen, so a device multiple-text-nodes-in-one-row objection is weaker evidence than the same objection in a unit test.

Researcher-reported, un-itemised: reading the review screen after the 18:28 run, non-message on-screen text appeared to be counted as messages. Recorded as a qualitative observation. No classifier rule was added in response — tuning against one unlabelled screen overfits to Instagram's chrome and risks deleting real messages.

Open defect: review-screen text overlap

Reporting 16–17 records made adjacent rows print over one another. Cause: each record was drawn as two separate text layers (a small header line plus a body line) inside a selection container nested in a scrolling column. Fix applied: one text layer per record, and the list sets its own spacing. Tests re-run at 18:33 → 156/0/0/0, then a full --rerun-tasks build, installed successfully and relaunched.

This fix is reasoned, not visually confirmed. It cannot be confirmed by this harness — a screenshot of that screen would write Instagram message text into a file, which the privacy rules forbid. The researcher must confirm it on the next run. The test emulator is currently switched off, so the layout is unverified and the run log buffer is gone (all quoted lines above are preserved in the project's own documentation).

10. Next research milestone

  1. Produce one consented, hand-transcribed thread — the transcription method is already defined in the compatibility report. This is the critical path: it converts the first NOT MEASURED rows into denominator-bearing numbers and makes ladder level 4 reachable.
  2. Itemise the false positives — 3–5 annotated "this record is wrong because it is ___" lines, which turns the qualitative observation on page 8 into a rate and justifies specific, isolated rules.
  3. Confirm the layout fix visually and record which ladder levels a real screen reaches.
  4. Label the unlabelled rows (R4–R8, RC-01, RC-02) so existing evidence can be read as thread-screen evidence.
  5. Characterise the crowded-row failure on a real app before trying to improve recall.
  6. Find a lawful positive-timestamp signal; without one, no time-ordered analysis is defensible.
  7. Only then run the extraction → preprocessing handoff on real data — still with the model un-integrated, still only the researcher's own consented text.

Explicitly out of scope, permanently: scrolling, history navigation, clicking, background monitoring, notification/clipboard/keystroke routes, view-ID-keyed rules, extra permissions, network transmission, and model training on extracted text.

11. Glossary in plain language

TermWhat it means here
Accessibility nodeOne widget on screen as Android describes it to assistive technology — a class name, optional text, an optional description, a rectangle, and child widgets.
Tree / traversal / BFSScreens nest like folders inside folders. A traversal visits every one; breadth-first means "finish this level before going deeper".
RootThe outermost node. "root = false" means Android would not hand over the screen at that instant — usually a transition frame.
ArmingPressing Start. The tool waits for one qualifying event, reads once, then disarms itself.
withTextNodes exposing real text — the actual text surface, and the column that matters for messages.
descOnlyNodes with only a content description: a label written for a screen reader about a control ("Send button"), not message content.
Text-bearingThe two above added together. Never quote it alone — it hides which kind of text you are looking at.
Candidate / accepted / ambiguous / rejectedLooks like a message but not accepted yet / confident / genuinely unsure, so kept and marked / concluded to be interface furniture, with a stated reason.
Container echoA wrapper widget repeating its child's text. Counting both would double the conversation, so the wrapper is dropped and the child kept.
Geometry orderingSorting by on-screen position (top to bottom) rather than by the order the widgets happened to be listed.
Partial visible sampleThe thread ran off the edge of the screen, so what was captured is not the whole conversation.
Ladder levelThe five separate claims a run can make, from "inspection completed" up to "complete conversation validated". Each needs its own proof.
Ground truth / annotated sampleA version of the screen transcribed by hand, so output can be compared against something. Its absence is why real-app accuracy is NOT MEASURED.
HandoffPassing accepted records to the text-cleaning stage. The model itself is not connected, so nothing is classified.
NOT MEASUREDThe comparison data does not exist. Different from 0, which would mean it exists and the tool scored nothing.

One-sentence conclusion. The prototype now genuinely rebuilds visible screens into ordered message records, refuses to invent anything it cannot see, keeps its privacy guarantees intact under real data, and has run against real Instagram three times — and the honest state of the research question is that none of that yet constitutes evidence that the reconstruction is correct, because the one missing ingredient is a hand-transcribed conversation to compare against.

13. Decisions that governed this phase

  • Never enable or arm programmatically. The accessibility toggle is a human-only act; three workarounds were offered and all three were refused, and the refusals are recorded in the project logs.
  • Never fill a row from a plausible number. An unmeasured metric is written NOT MEASURED; a genuine zero is written as a zero and explained; nothing is back-filled from a remembered value.
  • Build success is not extraction success. Every claim here is separated into what compiled, what was tested, what was observed on a device, and what remains unproven.
  • No accuracy claim without ground truth, and no compatibility claim for an app that was never installed.
Verification policy used throughout: no test is reported as passing unless it was executed and its output read; no metric is reported without its denominator; an unmeasured metric is written NOT MEASURED, never zero; a build succeeding is not a claim that extraction works; and the accessibility-service consent gate has never been automated or worked around.  ·  Report compiled 2026-10-21 from the executed log in docs/12 and the validation data in docs/13.
